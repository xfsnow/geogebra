### 引用重写方法（重要）
HTML 是 Antora 3.1.14 生成，站内引用统一为「N 个 `../` 上跳到仓库根 + 根相对路径」的形式
（如 `../../../../manual/en/tools/X/`），**不能**用字符串替换。采用的算法：
1. 用文件**旧**目录解析相对引用 → 仓库根相对的旧绝对路径
2. 按 `manual/en/_images→images`、`manual/en→en`、`manual/zh→zh` 映射到新路径
3. 从文件**新**目录重新计算相对路径

脚本在系统临时目录：`ggb_migrate.py`(改写) / `ggb_verify.py`(迁移前后对比) / `ggb_verify_post.py`(迁移后校验)。

### git rename 检测的坑（重要认知）
- **git 提交本身不存储 rename 信息**，rename 完全是 `git diff/log/show` 时实时计算的
- 因此 commit 内容无论怎样都一样；显示为 R 还是 A+D 只取决于查看时的 `-M` 阈值和 `diff.renameLimit`
- 本次 1772 个移动：395 图片 + 1 md 是纯改名（100% 识别为 R）；1376 个 HTML 因内容大幅改写，
  仅 835 个能识别为 R，541 个相似度低于 50% 退化为 A+D
- 实测把 `--find-renames` 从 50% 降到 5% 结果完全不变，说明瓶颈是内容差异而非阈值
- 若要历史完全干净，应拆两个 commit：先纯 `git mv`，再提交内容改写
- 查看时可用 `git -c diff.renameLimit=20000 diff` 提高识别数（不要去改用户的 git config）

### basename 全文搜索的两个误判（教训）
- `highlight.js` → 命中的是外链 `https://cdnjs.cloudflare.com/ajax/libs/highlight.js/11.11.1/...`，非本地文件
